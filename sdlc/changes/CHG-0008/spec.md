# Spec: Hosted-mode sync fast-forwards main without requiring it checked out

The intent (accepted at gate 1, sha `280f9724`) names one failure. Every hosted-mode pass that brings `origin/main` into the local default branch first calls `requireOnBase` (`packages/server/src/github/artifacts.ts:81`), which refuses with `hosted mode merges into main; the working tree is on <branch>` whenever the project root is on any other branch. The engine runs that pass on every tick (`engine.ts:363`), so a developer who checks a task branch out in the root sees the 409 as a persistent error, merges done on the host stop being recorded and the records PR stops being pushed until they switch back. The guard exists because `mergeRemoteBranch` (`packages/adapters/git/src/remote.ts:24`) runs `git merge` in the root working tree, which needs the branch checked out; a fast-forward of a ref does not. This spec turns the intent into checkable requirements, fixes the design, and names one thing the intent did not: the guard was also the only thing keeping a merge-detected gate decision on `main`.

## Requirements

R1. **Root on the default branch: nothing changes.** With the root checked out on `main`, each of the three sites (`acceptViaPr`, `detectMergedPrs`, `syncRecords`) syncs exactly as today: `git fetch origin main`, `git merge --ff-only FETCH_HEAD`, and when that fails a merge commit under `mode.identity` (committer `mode.committer` under a GitHub App) with the same message as before (`sdlc(<CHG>): sync origin/main after #N` or `sdlc: sync origin/main`). The existing GitHub-mode tests pass unchanged.

R2. **Root on another branch, origin ahead only: the ref moves, nothing else does.** With the root on `CHG-NNNN/<slug>` and `origin/main` strictly ahead of local `main`, a pass updates `refs/heads/main` to origin's head with `git fetch --quiet origin main:main`. No commit is created, no worktree is created, and the root's `HEAD`, index and working tree are untouched (`git status --porcelain` before and after are identical). `refs/remotes/origin/main` is updated by the same fetch. The pass records or pushes whatever it came to do, and no error is logged.

R3. **Root on another branch, histories diverged: a real merge, off the root.** With the root on a task branch and local `main` carrying commits origin lacks, git refuses the fast-forward (the refspec has no `+`, so a non-fast-forward is rejected). The pass then merges `origin/main` into `main` in a working tree that has `main` checked out: the existing worktree that has it, otherwise a temporary one created and removed by `withBranchWorktree`. The merge commit has both parents, is authored by `mode.identity` and committed by `mode.committer`, carries the same message as R1, and every local commit stays reachable from `main`. Afterwards no `tmp-*` directory remains under `.sdlc-state/worktrees/` and `git worktree list` shows nothing new. The root's `HEAD` and working tree are untouched.

R4. **Never force.** The refspec is `main:main`, never `+main:main`; `--update-head-ok`, `--force` on `git worktree add`, `git reset`, `git stash` and `git checkout` of the root are never used by this path. A diverged history is resolved by R3 or refused; local commits on `main` are never discarded. There is no flag, environment variable or config key that relaxes this.

R5. **The 409 is gone.** `requireOnBase` is deleted and the message `hosted mode merges into <base>; the working tree is on <branch>` appears nowhere in `packages/`. `acceptViaPr`, `detectMergedPrs` and `syncRecords` succeed from a root on a task branch, and the engine's log has no line for that reason.

R6. **Merge detection records the decision on `main`, whichever branch the root is on.** When `detectMergedPrs` records a PR merged on the host, the `gate.accepted{source: pr.merge}` commit (and its `stage.entered`, plan front-matter or loop archive) lands on `refs/heads/main`, derived from `main`'s tree, not on the branch the root has checked out. Done signal: after a pass with the root on a task branch, `git log main -1` is the recording commit, `git log <task branch> -1` is unchanged, and `git show main:sdlc/changes/<CHG>/log.jsonl` carries the event. Today the commit goes to the root's `HEAD` (`artifacts.ts:315`), which R5 alone would send to the task branch (C1).

R7. **Accepting through a PR works from a task branch.** `acceptViaPr` with the root on a task branch commits the decision on the PR branch (already via `commitOnBranch`), merges the PR through the API and brings origin's merge into `main` by R2 or R3. The returned `mergeSha` and `number` are as today.

R8. **The records PR works from a task branch.** `syncRecords` counts `main..origin/main` and `origin/main..main` by ref, syncs by R2/R3 when behind, and pushes `refs/heads/main:refs/heads/sdlc/records` as today. None of it reads the root's checkout.

R9. **Gate 5 through the console is unchanged.** The check at `actions.ts:67` (`gate 5 merges into main; the working tree is on <branch>`), the hosted `merge` in `adapter-github/src/codehost.ts:238` and `adapter-gitlab/src/codehost.ts:244`, and `cli/src/commands/gate.ts:59` keep their behaviour: they merge a task branch into `main` in place and still need `main` checked out (C4).

R10. **A human's dirty worktree is refused, never merged into.** When the fast-forward is refused and `main` is checked out in a pre-existing worktree whose `git status --porcelain` is not empty, the pass does not run the merge there. It fails with an error that names the worktree path and what to do (`main is checked out at <path> with uncommitted changes; commit them or check out main in the project root`). `acceptViaPr` surfaces it as a 409; `detectMergedPrs` as the engine's `merge detection: …` line; `syncRecords` as `records.error`. Nothing is stashed or reset (C2). A clean pre-existing worktree is merged in and left on the merge commit.

R11. **Tests.** In `packages/server/test/github.test.ts`, with the fixture clone checked out on a task branch before the engine's pass:
- R2: origin moved (a records PR or an artifact PR merged on the fake host), local `main` equal to the old origin: after `engine.sync()`, `main` equals `origin/main`, `git log main` has no merge commit, the task branch head and `git status --porcelain` are unchanged, no `tmp-*` worktree exists.
- R3: the same with a local lifecycle commit on `main` first: `main` has a merge commit with two parents whose message is the sync message, the local commit is an ancestor of `main`, no `tmp-*` worktree remains, root untouched.
- R3 with `main` checked out in a second worktree of the clone: the merge commit lands and that worktree is on it; a dirty variant of the same test proves R10.
- R6: a spec PR merged on the fake host with the root on a task branch: `gate.accepted{2}` is on `main` and not on the task branch, and the next pass reports `already recorded`.
- R7 and R8: an accept through the console and a records push, both from a task branch.
- In `packages/adapters/git/test/`: `fastForwardBranch` returns the fast-forwarded head when origin is ahead, reports "up to date" when equal, and reports a refusal without touching the ref when local is ahead, when the branch is checked out in the same clone, and when it is checked out in another worktree.
`pnpm build`, `pnpm test` and `pnpm lint` are green from the root checkout with the output pasted into the plan's proof.

R12. **Files that change.** `packages/adapters/git/src/remote.ts` (new `fastForwardBranch`), a test file beside the adapter's existing tests, `packages/server/src/github/artifacts.ts` (the three call sites, `requireOnBase` removed, D2 and D4), `packages/server/test/github.test.ts`, and one row in `docs/decisions.md` (`CHG-0008`) recording why the sync no longer needs `main` checked out and why the decision commit is redirected. `actions.ts`, the code-host adapters, the CLI, the MCP server and the hooks are untouched (C6).

## Design

D1. **`fastForwardBranch(dir, branch, remote = "origin")` in `remote.ts`.** Runs `fetchRemote(dir, remote, branch)` first, so a network or auth failure throws through `git()` as today and is never mistaken for a refusal. Then `gitRaw(dir, ["fetch", "--quiet", remote, `${branch}:${branch}`])`: exit 0 is success, and the function returns `{ head, moved }` by comparing `rev-parse refs/heads/<branch>` before and after. A non-zero exit after a fetch that just succeeded is git refusing the ref update, and the function returns `{ refused: true, reason: stderr }` without throwing. Git refuses in exactly the cases the intent lists: the update is not a fast-forward (`! [rejected] … (non-fast-forward)`, because the refspec has no `+`), or the branch is checked out in this or any linked worktree (`refusing to fetch into branch 'refs/heads/main' checked out at '<path>'`). The function never passes `--update-head-ok`, never writes the ref itself with `update-ref` (that would move a branch under a checked-out worktree and leave its index stale, which is what git's refusal protects), and creates no commit, so it needs no identity. It is exported from `@sdlc/adapter-git` like `mergeRemoteBranch` and reachable from nothing agent-facing (C7).

D2. **One `syncBase(mode, store, base, message)` in `artifacts.ts` replaces the three `requireOnBase` + `mergeRemoteBranch` pairs (lines 204/217, 289/290, 348/349).** In order:
1. `currentBranch(root) === base` → `mergeRemoteBranch(root, …)` exactly as today (R1). A detached root (`HEAD`) falls through to step 2.
2. `fastForwardBranch(root, base)`; when not refused, done (R2). A `moved` result is logged through `mode.log` (`main: fast-forwarded to <sha7>`); an up-to-date one is silent.
3. Refused → find the worktree that has `base` checked out with `listWorktrees(root)`. If there is one and its `git status --porcelain` is not empty, throw `ActionError(409, …)` naming the path (R10, C2). Otherwise `withBranchWorktree(root, base, (dir) => mergeRemoteBranch(dir, base, message, mode.identity, "origin", mode.committer))` (R3): the existing worktree when there is one, a temporary `.sdlc-state/worktrees/tmp-*` otherwise, removed in `finally`. `git worktree add` on a branch already checked out elsewhere fails without `--force`, which is why the existing-worktree lookup comes first and why no force flag is added (R4).
The message argument keeps today's two texts; the fast-forward path creates no commit and ignores it. `syncBase` returns the resulting head of `base` for the log.

D3. **Why fetch-then-fetch rather than one command or plumbing.** A single `git fetch origin main:main` would be ambiguous on failure (network, auth, refusal) and `mergeRemoteBranch` already separates fetch from apply; keeping that split means `FETCH_HEAD` is set once and both paths read it. `git merge-tree --write-tree` plus `commit-tree` and `update-ref` would give a merge without any worktree, but `update-ref` bypasses git's checked-out-branch protection and the intent asks for `withBranchWorktree`, which already exists and is used by `commitOnBranch` and `proposals.ts:42`. The worktree route is the one the codebase already trusts.

D4. **Merge detection writes on `base`, not on `HEAD` (R6, C1).** In `detectMergedPrs`, after `syncBase`, the loop that records each merged PR today calls `viewFor(repo, c.id)` on the store's snapshot (derived from the root's `HEAD`, `store.ts:123`) and `commitWritePlan(store.root, …)`. When the root is on `base` that is correct and stays as is. When it is not, the view is derived from `base`: `readTreeWithBranches(store.root, base)` → `loadRepo(tree)` → `deriveChange`, so `accept` runs against `main`'s ledger and artifacts (the merge just brought in), and the write goes through `commitOnBranch(store.root, base, result.plan, actor, mode.committer)`, which reuses `withBranchWorktree` and therefore the same dirty-worktree rule as D2. `StoreOptions.ref` (`store.ts:31`) exists and is unused; a base-pinned store built from it is an acceptable way to get the same view without a second loader, and the plan picks one. `store.refresh(true)` still follows the root's `HEAD` (decisions 1.1, C3): the snapshot does not change when the root is elsewhere, and the pass does not pretend otherwise. `openArtifactPrs` and `syncRecords` read refs (`base...branch`, `origin/base..base`) and need no change.

D5. **What stays as it is (R9, C4).** Gate 5 through the console merges a task branch into `main` in place: `actions.ts:67` and the hosts' `merge` still need `main` checked out. The intent scopes that out, and a developer working off `main` has a working path already: merge the code PR on the host, and `detectMergedPrs`, fixed here, records it on the next pass. The CLI's `gate.ts:59` check is the same rule. The local-mode artifact accept (`actions.ts:86` onward) is not hosted mode and keeps its check.

D6. **What the user sees.** The persistent 409 disappears from the engine's log and the UI. Three things remain visible by design: a `main: fast-forwarded to <sha7>` log line when the ref moved; a merge commit on `main` when histories diverged; and, only when their own `main` worktree is dirty, one actionable error naming the path (R10). While the root is off `main` the console shows the task branch's `sdlc/` (C3); switching back shows what the pass recorded.

D7. **Adapter surface.** `mergeRemoteBranch` is unchanged. `withBranchWorktree` is unchanged in behaviour; if the plan needs the pre-existing/temporary distinction for the dirty check, it does the `listWorktrees` lookup in `syncBase` rather than widening the helper's signature. Nothing new is exported from `@sdlc/server`.

## Open questions carried forward

- **A persistent `main` worktree instead of a temporary one (from C5, R3).** A long-lived `.sdlc-state/worktrees/main` would make every non-fast-forward sync a merge in an existing checkout and remove the per-pass full checkout. It changes what `withBranchWorktree` finds for every caller (`commitOnBranch`, proposals) and needs a pruning story with 3.2's stale-worktree cleanup. Carried for the tech lead as its own change; this one uses the temporary worktree the intent names.
- **Should the whole sync pass derive from `main` when the root is elsewhere? (from D4, C3).** D4 redirects only the merge-detection write, because that is where a wrong branch would put a human decision in the wrong place. `openArtifactPrs` still reads the `HEAD`-derived snapshot (`docs[i].state`, `artifactPrs`) and is protected by its ref-based `base...branch` diff, and the UI stays on the root's view by decision 1.1. A base-pinned store for the engine's pass (the unused `StoreOptions.ref`) would make every read consistent; carried for the tech lead.
- **Other engine commits still land on the root's `HEAD` (from C1).** `runner.ts:148`, `review.ts:56`, `suite.ts:121`, `engine.ts:214` and `:681`, `records.ts:107` and `intake/webhooks.ts:121` all call `commitWritePlan(root, …)` and rely on the root being on `main`. Same class as C1, outside the three sites the intent names. Carried for the tech lead as a change of its own ("engine commits target the default branch by ref").
- **Gate 5 through the console from a task branch (from C4).** The console's own gate 5 merge and the CLI's still need `main` checked out. Whether they should go through the same worktree route is a separate change; merging on the host covers the case meanwhile.
- **Git's refusal texts (from D1).** This session could not run a scratch repository (the shell probe was denied), so the two refusal messages in D1 are quoted from git's documented behaviour and the fast-forward rule from the refspec semantics. The plan's first step runs them once and pastes the output, and the adapter test (R11) pins them.
- **Resolved here, recorded for the plan:** fetch first, then the `main:main` refspec (D1, D3); one `syncBase` helper for the three sites (D2); refuse a dirty pre-existing worktree, never stash (D2, C2); merge detection derives from and commits on `main` when the root is elsewhere (D4); gate 5 and the code-host `merge` untouched (D5).
